    SIPANEL STEP 2C-HARDENING 20260922T083014Z: immutable demand provenance, Native Owner boundary, governed Sales cancellation, safe restore instructions
    
    Four independent-review findings on STEP 2C (e01da19), corrected on top of it.
    
    1. Execution-demand provenance is now behaviourally immutable
       (sipanel_scope_execution 19.0.1.0.2). readonly=True never prevented ORM,
       RPC, sudo or import writes. sipanel.execution.demand.create() now requires
       the process-local engine token (guard(env, 'sipanel_demand_engine')), opened
       only by _release_locked, the amendment-delta engine and the governed batch
       cancellation. write() refuses every provenance/ownership field after
       creation - batch, Scope, component, delta uid, mode, owner, demand_key,
       quantities, uom, product, Project/System/Activity, reversal lineage - for
       everyone including the engine (a change is a new delta demand), and refuses
       any other field (state, reversal_required) unless the engine token is
       present. unlink() is always refused. A raw context flag, a guessed token,
       sudo() and import_file open nothing. reversal_of_id / cancelled_by_delta_uid
       are now part of the delta demand's creation values instead of a later write.
    
    2. Native Owner boundary in cancellation and reduction. cancel_delta() and
       reduce_planned() no longer cancel, reduce or rewrite targets SIPANEL only
       linked (native_anchor_covered / linked_existing): the native Sale line owns
       its delivery move, task or purchase line and SIPANEL only records its own
       lineage. Bridge-created draft documents are still withdrawn (PO line qty 0,
       MO cancel, move cancel, picking cancel). reversal_required is now a
       classification of executed targets (done move/picking, produced MO,
       confirmed/received PO line, posted analytic line) instead of an else-branch:
       a linked project or an already-cancelled picking no longer raises operator
       noise. Repeated cancellation is idempotent (cancelled batches and demands
       are skipped, one audit row per real cancellation). Order cancel refuses only
       on executed documents SIPANEL created itself.
    
    3. Governed Sale Order cancellation without broad demand rights.
       sale.order._action_cancel now checks the caller's native write access on the
       order (ACL + record rules) first, then transitions only that order's
       batches as sudo with the engine token. sudo() keeps env.uid, so the
       initiating Sales user is the actor of the 'execution_cancel' audit row.
       Sales users keep no create/write/unlink access on demands; a direct
       demand write, a batch action on another order, or a forged engine context
       are all refused with AccessError.
    
    4. scripts/sipanel_recovery_point.sh prints a safe restore REHEARSAL procedure
       (unique rehearsal database and filestore names, archive layout inspection,
       extraction into a temporary directory, installation only under the
       rehearsal filestore name, integration neutralisation before any Odoo
       process, validated and marked DESTRUCTIVE cleanup) and gains a
       non-destructive `restore-instructions <point>` mode. The unsafe one-liner
       that extracted onto the live filestore is gone.
